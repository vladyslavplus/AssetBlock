# Analysis data removal and backups

## Retention clocks and protection

`AbandonedUploadRetentionWorker` uses each uploaded `AssetVersion.CreatedAt` as the 30-day clock and only retires the payload when every stored version has passed the cutoff. It considers at most 100 eligible candidates per daily cycle; unknown, blank, and literal `null` provider generations are excluded before the limit and counted in an error log so they cannot starve later candidates. Inside an asset-row transaction it rechecks version age, moderation/publication history, active analysis and security work, active processing jobs, purchases, active or provider-bound checkouts, and unresolved reconciliation holds. A protected upload keeps its bytes. An eligible upload is tombstoned and its versions receive `StorageRetiredAt`; immutable version identities, archive/malware evidence, terminal analysis runs, and other proof rows remain in PostgreSQL. Exact encrypted payload versions are queued for asynchronous deletion. A submission with a rejected state remains protected because this schema has no authoritative final-decision and closed-appeal timestamps; no 90-day decision is inferred.

`CodeAnalysisRetentionWorker` uses report `FinalizedAt` and calendar-month arithmetic for finding/reuse detail and matching audit rows. It also uses each `AssetArchiveAnalysis.CreatedAt` for private extracted README and manifest payloads, including rows without a finalized report. After 12 calendar months, the worker nulls `ReadmeContent` and `ManifestMetadata` in bounded batches (250 rows, at most 20 batches per data type per cycle), while retaining archive `FileCount`, `TotalExpandedBytes`, timestamps, version/hash identities, security evidence, runs, report headers, admitted counts, stages, and publication/access proof. It defers when purchases, publication snapshots, active/pending or provider-bound checkouts, active or rejected moderation submissions, queued/running analyses or security rechecks, active processing jobs, or unresolved reconciliation holds exist. Rejected submissions stay protected because final-decision and closed-appeal timestamps are not represented. Seller history continues to show its summary and count and marks finding detail unavailable when retained rows no longer match that count. Owner findings count, summary visibility, and page rows use one repeatable-read snapshot, so concurrent detail removal cannot produce a shortened page marked available. Commerce and unrelated audit rows are not age-deleted.

## Source eligibility and object deletion

An asset tombstone commits before any delayed physical cleanup. Catalog, sale, embedding, and recommendation eligibility require `DeletedAt IS NULL`, so a tombstone stops new product-source comparisons immediately, including DB-backed similarity candidate queries. The pinned code-analysis reference manifest is a separately governed, immutable research corpus, not a snapshot of product assets; current product-comparison logic does not ingest product assets into that index. Tombstoning a product therefore does not rewrite that research snapshot. Analysis admission and finalization recheck the asset tombstone. Plaintext analysis workspace files are bounded and transient; extracted archive README and manifest metadata are separately retained in PostgreSQL for at most 12 calendar months before eligible redaction under the protections above.

Each new upload uses the app-generated per-version key and records the immutable provider `VersionId` returned by the S3-compatible write. Cleanup outbox payloads carry asset, asset-version, key, and storage-version identity; dispatch validates that exact identity and rechecks current relational references and protections immediately before deleting the exact provider version. Retired payload rows retain their proof identity and remain references for the orphan sweep; only the guarded retirement outbox path may delete a retired row's payload. Replayed deletes target the same version and are safe after a crash following storage success. The orphan sweep evaluates at most 250 listed versions for age, protection, and deletion per daily cycle. A singleton PostgreSQL cursor stores S3 `key-marker` and `version-id-marker` values plus a lease. It requests `ListObjectVersions` pages capped at 250 and advances the durable marker only after every item in that page has been checked; interrupted pages replay safely. The explicit `IsTruncated` response determines completion, including end-of-list wraparound. If a saved version disappears, its marker remains an ordering position; provider errors or missing/non-advancing markers fail the scan without clearing progress. The installed MinIO .NET 7 high-level stream does not paginate version listings with S3 version markers, so the worker uses the S3 `ListObjectVersions` API directly. The supported pgsty MinIO test build appends an internal `[minio_cache:v2,...]` sentinel to `NextKeyMarker`; the parser recognizes that response and uses the final returned version's exact key with the provider's version marker. Listing calls are page-bounded and the worker renews its lease before listing and before each destructive check. Delete markers are traversed but never treated as encrypted payloads. The sweep deletes only truly unreferenced objects when listing returned an exact version ID; missing IDs are retained and logged.

The `StorageVersionId` and `StorageRetiredAt` columns require their generated EF migrations before this code can run against an existing database. Existing rows have no trustworthy provider generation, so the 30-day sweeper retains them and hard deletion skips their blob cleanup. The orphan sweep can delete such a blob only if provider listing returns its exact version ID and no database reference or protection remains; otherwise it retains the object for operator investigation. Bucket versioning must be enabled and verified before accepting uploads; the application does not enable it. A bucket without versioning returns no usable generation and new uploads fail closed, retaining any already-written object for investigation/orphan handling.

The pinned code-analysis manifest/index is not rebuilt or edited by asset deletion. It is a separately governed research snapshot, outside product asset eligibility. A future change that places product assets into that corpus must add an eligibility snapshot gate before deployment; this change does not authorize corpus expansion.

## Live database, blobs, and backups

Database detail removal and asset deletion occur in bounded PostgreSQL transactions. Blob deletion is asynchronous through the leased/retryable outbox; an asset can be tombstoned or removed from the database before its exact blob version is physically deleted. Missing provider generations, relational protections, or storage failures retain/defer data rather than fall back to deleting by key.

Database restore can reintroduce deleted rows. Object-store versioning, replication, snapshots, database backup schedules, backup retention periods, and purge procedures were not verified for this deployment. A restore may make old rows or blob versions available again. No compliant erasure or backup purge guarantee can be inferred from live database and object deletion alone.

The current persistence model has paid reconciliation holds but no separate dispute lifecycle record. Cleanup can protect unresolved holds represented in the database; dispute protection beyond those records is not implemented or verified.
